# PDF Nova — Security & Privacy Notes

Scope: what the app protects, how, and what it does **not** protect against.
Code references are relative to the repository root.

## 1. Vault encryption

Implementation: [lib/services/vault_service.dart](../lib/services/vault_service.dart) · UI: [lib/features/vault/vault_screen.dart](../lib/features/vault/vault_screen.dart)

| Aspect | Design |
|---|---|
| Cipher | **AES-256-GCM** (authenticated encryption) from [`package:cryptography`](https://pub.dev/packages/cryptography). On Android `cryptography_flutter` routes it to the platform's native implementation; tests use the pure-Dart implementation of the same algorithm. No custom cryptography. |
| Key | One random 256-bit key per install, generated by the library's secure RNG. |
| Key storage | `flutter_secure_storage`: Android Keystore–wrapped; never leaves the device. Never hard-coded, never written to app files or logs. |
| Biometrics | `local_auth` gates the **UI**. The key is deliberately **not** bound to biometrics, so enrolling a new fingerprint/face cannot make the vault unreadable. Device PIN is accepted as fallback; with no lock screen at all, the vault refuses to open. |
| File format | Per document: `<id>.nvd` (content) + `<id>.nvm` (metadata JSON: name, size, date, SHA-256). Blob = `PNV1` · 12-byte random nonce · ciphertext · 16-byte tag. Associated data `PNV1|kind|id` binds each blob to its entry, so swapping blobs between entries fails authentication. File names are encrypted (stored only inside `.nvm`). |
| Integrity | GCM tag verified on every decrypt; plaintext SHA-256 re-checked against the metadata. Damaged entries are shown as "Cannot be decrypted — kept, not deleted". |
| Atomic writes | Every blob is written to `*.tmp`, flushed, then renamed. Metadata is written last, so an entry only exists once both parts are complete. A failed write (e.g. disk full) removes everything it wrote. |
| Crash debris | On every listing, leftover `*.tmp` files and data blobs without metadata (an add that never finished — its source was never removed) are deleted. Complete entries and legacy plain files are never touched. |
| Key loading | Loaded once and memoised, so concurrent first use can't create two keys. A secure-storage read error or a malformed key raises `VaultKeyUnavailableException`; **no replacement key is ever created** in that case. |
| Viewing | A decrypted copy is written to the app's private temp dir (`<tmp>/vault_open/<id>/`) only when the user opens a file, opened in PDF Nova's own Reader (never handed to another app; screenshots stay blocked), and deleted when the Reader closes, or when the vault locks, the screen is left, the next vault visit starts, **or the app next starts** (covers a killed process). |
| Lock policy | Locks when you tap the lock button, leave the vault screen, or the app goes to the background — except for the vault's own file picker, so adding a file doesn't lock you out. Coming back **after more than 2 minutes** re-locks even then. Locking also closes a Reader showing a vault file. Process death always means locked. Failed or cancelled authentication leaves it locked. |
| App switcher & screenshots | While the vault screen is shown the window is `FLAG_SECURE`: the app-switcher preview is blank and screenshots/screen recording show black. |
| Backups | `android:fullBackupContent` / `android:dataExtractionRules` exclude the vault folder and the secure-storage prefs ([backup_rules.xml](../android/app/src/main/res/xml/backup_rules.xml), [data_extraction_rules.xml](../android/app/src/main/res/xml/data_extraction_rules.xml)). The Keystore key is never backed up, so restoring encrypted files elsewhere would only produce unreadable data. |

### Key-loss behaviour
If encrypted files exist but the key is missing (e.g. app data partially cleared), the service **refuses to create a new key** (`VaultKeyMissingException`) — a new key would orphan the files forever. Files are never deleted automatically.

### Migration from the old plaintext vault
Older versions stored PDFs in `PDFNovaVault/` unencrypted. On unlock the vault shows "N older files are not encrypted yet → Encrypt". Migration is user-initiated and per file: encrypt → decrypt the new copy → compare SHA-256 → only then delete the plain original. Any failure removes the partial encrypted copy and leaves the original untouched; the result is reported.

**Interrupted migration** (app killed after encrypting, before removing the original): the next run finds an existing encrypted entry with the same name *and* SHA-256, verifies it decrypts to the same bytes, and only removes the original — no duplicate is created. A same-named file with different content is migrated as a separate entry.

### What the vault does not protect against
- A device that is already compromised (rooted, or malware with your screen-lock).
- Someone who knows your device PIN.
- Copies that left the vault on purpose: files you shared or saved to Downloads.
- A device that can't keep the Keystore key (e.g. some devices invalidate keys when the screen lock is removed). Then the files cannot be decrypted; the app says so and never deletes them.

## 2. Generated files and deletion safety
- Every output is written to `<name>.part` and renamed only when complete (`writeAtomic`); every generated PDF is re-opened and its page count checked before it is saved; DOCX/PPTX packages are re-opened and structurally checked. A failed run leaves no partial file and no history entry.
- Every PDF output is rewritten as **one revision** (reload + full save, then re-verified). A plain save appends to the source, so the original stayed inside the output as an earlier revision — truncating at the first `%%EOF` recovered the un-watermarked, unstamped or unfilled document. Protected outputs are already written whole by the encryptor (checked: no plaintext of the source remains).
- Outputs are written to `<app documents>/PDFNova/` (app-private).
- The Files tab can **rename/delete only files inside app storage** (`FileService.isAppOutput`, which also rejects `..` path tricks). For anything else it only removes the history row.
- "Remove from history" never touches the file; "Delete file" asks for confirmation and states that originals, Downloads copies and shared copies are unaffected.
- Original documents the user picked are never modified or deleted by any tool.

## 3. Network
- No document, text, OCR result or metadata is sent anywhere. The app has no analytics or ads SDK active (ads are disabled).
- `INTERNET` permission exists only for **WiFi Share**, a local HTTP server serving exactly one chosen file (other paths → 404) while its screen is open.
- **Known gap:** WiFi Share has no access token — anyone on the same network who learns or guesses the URL during the session can download that one file. Planned: random per-session token in the URL and multi-file sessions with expiry.

## 4. Notes
The quick note lives in Android SharedPreferences (shared with the Home-Screen widget) — app-private but **not encrypted**. Don't keep secrets in quick notes.

## 5. Logging
The app does not log document contents, passwords or keys. Tool errors shown to users are generic and contain no file contents.
